# 🔌 rndCRM — External API Documentation

> **Audience:** external systems calling INTO rndCRM — today, the main CRM's
> own backend. Not for rndCRM's own frontend (see `API_DOCUMENTATION.md` for
> that — different auth model entirely).
>
> **Base URL:** `http://localhost:5000/api` (dev) — swap for the deployed
> rndCRM origin in production.
>
> **Authentication:** two different models depending on the domain — most
> require a per-integration API key from **Admin → API Keys**; Lead
> Capture accepts the same key but doesn't require it. See
> [Authentication](#authentication) below.
>
> **Content-Type:** `application/json` (unless noted otherwise)

## Authentication

**Most domains (Lead Sync) require an API key.** Generated by an rndCRM
admin from **Admin → API Keys** in the sidebar. The key is shown **exactly
once**, at creation — copy it into your system's own server-side config
immediately. rndCRM never stores or re-displays the raw value again, only
a one-way hash.

**Send it as `secret`:**

| Request type | Where `secret` goes |
|---|---|
| `GET` | Query string — `?secret=<your key>` |
| `POST` | JSON body — `{ "secret": "<your key>", ... }` |

```
GET /api/lead-sync/pending?secret=rndcrm_xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx
```

**Rules:**
- Store the key in your backend's own environment config — **never** in
  frontend/browser code. Anyone who can read it can call every API-key
  endpoint in this document.
- One key currently grants access to every API-key domain (no per-domain
  scoping yet — see `backend/src/external-api/README.md` if that ever
  needs to change).
- An admin can revoke a key any time from the same page. A revoked key
  starts getting `401` on its very next request — no grace period.
- Missing or invalid key → `401 { "success": false, "message": "..." }` on
  every API-key endpoint; the specific message differs slightly by cause
  (missing vs. invalid vs. revoked) but the shape is always the same.

**Lead Capture is different — the API key is optional, and there's no
origin restriction.** Some callers (a truly frontend-only site's own
browser JS) have nowhere safe to keep a secret at all; others (a site
proxying its form through its own serverless function, e.g. a Netlify
Function) genuinely can. So this domain accepts the same `secret` param as
above, but doesn't require it:
- No `secret` sent → works anonymously, subject to rate limiting and a
  honeypot field instead of a credential.
- Valid `secret` sent → authenticated like any other API-key call, and
  exempt from the anonymous rate limit.
- Invalid/revoked `secret` sent → `401`, same as everywhere else — sending
  a bad key is never silently treated as sending no key.

See [§3](#3-lead-capture) for the details (short version: the no-key path
is not a hardened endpoint, and that's an accepted tradeoff for low-stakes
lead capture — use a key if your caller can hold one).

## 2. Lead Sync

Base path: `/api/lead-sync`. Keeps rndCRM's lead pipeline (source: web
form, Meta Ads, campaigns) in sync with the main CRM, in both directions,
plus lets the main CRM pull campaign email engagement for a lead.

### 2.1 Get Leads Pending Sync

Leads rndCRM created (via web-form capture, Meta Ads, or a campaign
conversion) that carry an `externalLeadId` from a *previous* sync but
haven't yet reached a terminal status. Poll this before pushing a batch of
status updates, so you don't have to fetch/filter your entire lead list —
rndCRM tells you exactly which ones it's still waiting to hear about. Once
a lead reaches `Won` or `Lost` it drops off this list on its own.

| Field | Value |
|---|---|
| **Endpoint** | `GET /api/lead-sync/pending` |
| **Auth** | API key (query string) |

**Example request**
```
GET /api/lead-sync/pending?secret=rndcrm_xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx
```

**Example response** — `200 OK`
```json
{
  "success": true,
  "data": [
    { "externalLeadId": "MAINCRM-8841", "phone": "+44 7700 900123", "status": "First Contact" },
    { "externalLeadId": "MAINCRM-9012", "phone": "+44 7700 900456", "status": "New Lead" }
  ]
}
```
`phone` is included because it's what the main CRM's own lookup typically
keys on; `externalLeadId` travels back unchanged for the status-sync call
below.

---

### 2.2 Push Lead Status

Called whenever a lead's status, deal value, or assigned agent changes in
the main CRM. Without this, rndCRM's own dashboards (Qualified Leads, Won
Customers, Revenue, ROI/ROAS on the Meta Ads page) stay stuck at whatever
the lead's status was the moment rndCRM first saw it.

| Field | Value |
|---|---|
| **Endpoint** | `POST /api/lead-sync/status` |
| **Auth** | API key (JSON body) |

**Body parameters**

| Field | Type | Required | Notes |
|---|---|---|---|
| `secret` | string | ✅ | API key |
| `externalLeadId` | string | ✅ | Must match a lead rndCRM already knows (set at creation) |
| `status` | string | one of `status` / `disposition` | Explicit rndCRM status: `New Lead`, `First Contact`, `Proposal Sent`, `Won`, `Lost` |
| `disposition` | string | one of `status` / `disposition` | Your CRM's own raw status/disposition name — rndCRM maps it internally, so you never need to know rndCRM's status vocabulary. Unrecognized values return `400`. Also stored verbatim as `externalStatusLabel` for display, regardless of which bucket it maps to. |
| `dealValue` | number | ❌ | |
| `externalAssignedToName` | string | ❌ | Display-only agent name |

Send **either** `status` or `disposition`, not both — `status` wins if both
are present.

**Example request**
```json
POST /api/lead-sync/status
{
  "secret": "rndcrm_xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx",
  "externalLeadId": "MAINCRM-8841",
  "disposition": "IVA Agreed",
  "dealValue": 4500,
  "externalAssignedToName": "DebtFree Path"
}
```

**Example response** — `200 OK`
```json
{
  "success": true,
  "data": {
    "leadId": "64f1a2b3c4d5e6f7a8b9c0d1",
    "status": "First Contact",
    "externalStatusLabel": "IVA Agreed",
    "dealValue": 4500,
    "externalAssignedToName": "DebtFree Path",
    "changed": true
  }
}
```

**Errors**
| Status | Cause |
|---|---|
| `400` | Missing `externalLeadId`, unrecognized `disposition`, or `status` not one of the 5 valid values |
| `404` | No rndCRM lead has that `externalLeadId` |

### 2.3 Get Lead Email Activity

The reverse of §2.2 — pulls everything rndCRM knows about outreach to a
given email address: every campaign it received (verification status,
send/open/click/reply/unsubscribe timestamps, "Request a Call" clicks) plus
any one-off emails sent from that lead's detail page in rndCRM. Intended to
be called on-demand — e.g. when an agent opens that lead in the main CRM —
not cached, since it reflects live tracking data.

| Field | Value |
|---|---|
| **Endpoint** | `GET /api/lead-sync/email-activity` |
| **Auth** | API key (query string) |

**Query parameters**

| Field | Type | Required | Notes |
|---|---|---|---|
| `secret` | string | ✅ | API key |
| `email` | string | ✅ | Looked up case-insensitively |

**Lookup behavior** — this endpoint does **not** require the email to
belong to a converted/synced `Lead` record in rndCRM. Most campaign
recipients never reach that bar, so the primary source is the campaign
send/open/click ledger itself; `data.lead` is `null` when the address was
only ever a campaign recipient. If more than one rndCRM lead happens to
share the email (no hard-unique constraint on that field today), the most
recently updated one is returned.

**Example request**
```
GET /api/lead-sync/email-activity?email=john@acme.com&secret=rndcrm_xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx
```

**Example response** — `200 OK`

## 3. Lead Capture

Base path: `/api/lead-capture`. Lead intake meant to be droppable into
**any number of external sites** immediately, with zero registration step
— unlike Lead Sync, there's no origin restriction either. The API key here
is **optional, not required** (see [Authentication](#authentication)):
sites with no backend of their own call it anonymously; sites that proxy
their form through their own serverless function (e.g. a Netlify Function)
can call it with a real key instead, which exempts them from the anonymous
rate limit. See "Auth models" in `backend/src/external-api/README.md` for
the full reasoning, including what the no-key path actually costs (short
version: it's reachable by anyone who finds the URL shape, not just your
own sites — the rate limiter and honeypot are the only defenses for that
path, an acceptable tradeoff for low-stakes lead capture, not for anything
higher-stakes).

### 3.1 Submit a Lead

| Field | Value |
|---|---|
| **Endpoint** | `POST /api/lead-capture/:source` |
| **Auth** | Optional API key (`secret` in the JSON body) — open to any origin either way |

`:source` is a free-form label identifying which site/campaign a lead came
from (e.g. `debtfreepath`) — it's just a string, not a credential and not
a registration requirement. Any value works immediately; optionally map a
slug to a nicer display name in
`backend/src/external-api/leadCapture/sources.js` (purely cosmetic — it
only affects the created lead's `utmSource`, unmapped slugs are used
as-is).

**Body parameters**

| Field | Type | Required | Notes |
|---|---|---|---|
| `name` | string | ✅ | Full name of the person filling the form |
| `email` | string | ❌ | |
| `phone` | string | ❌ | |
| `dealValue` | number | ❌ | |
| `companyName` | string | ❌ | Only relevant if the form actually collects one — falls back to `name` otherwise (this endpoint is for personal/consumer leads, not B2B) |
| `secret` | string | ❌ | API key, if the caller has one — see [Authentication](#authentication). Omit entirely for a caller with nowhere safe to hold one. |
| `website` | string | ❌ | **Honeypot** — a hidden field real visitors never see or fill. Leave it out of the visible form entirely; if a bot fills it, the submission is silently accepted (`201`) but no lead is created. |

**Example request — no key (frontend-only site)**
```
POST /api/lead-capture/debtfreepath
{
  "name": "Jordan Smith",
  "email": "jordan@example.com",
  "phone": "+44 7700 900123"
}
```

**Example request — with a key (server-side caller, e.g. a Netlify Function)**
```
POST /api/lead-capture/debtfreepath
{
  "name": "Jordan Smith",
  "email": "jordan@example.com",
  "phone": "+44 7700 900123",
  "secret": "rndcrm_xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx"
}
```

**Example response** — `201 Created`
```json
{ "success": true, "data": { "leadId": "64f1a2b3c4d5e6f7a8b9c0d1", "leadRef": "LD-1042" } }
```

Both requests above produce the same response shape. The lead is created
with `source: "Web Form"` and `utmSource` set to the resolved source
label, so it's immediately visible and filterable in the normal Leads
Pipeline either way — the difference between the keyed and unkeyed request
only shows up in the lead's activity log (notes whether it came in via a
verified key or anonymously) and in whether it counted against the rate
limit.

**Errors**
| Status | Cause |
|---|---|
| `400` | Missing `name` |
| `401` | A `secret` was sent but doesn't match any active key (a *missing* `secret` is not an error — that's the anonymous path) |
| `429` | Rate limit exceeded (20 requests/minute per IP) — never triggers for a request authenticated with a valid key |

**Adding a new site:** nothing required — just start POSTing to
`/api/lead-capture/<any-label-you-want>`, with or without a key. Add an
entry to `sources.js` only if you want a nicer display name than the raw
label in reporting; create a key from Admin → API Keys only if that site
has somewhere safe to hold one.

## 4. Error Handling

Every error response, on every endpoint in this document, has the same
shape:

```json
{ "success": false, "message": "Human-readable reason" }
```

| Status | Meaning |
|---|---|
| `400` | Bad request — missing/invalid parameter |
| `401` | Invalid or revoked API key — required on Lead Sync; on Lead Capture, only triggers if a `secret` was sent and didn't match (a missing `secret` there is not an error) |
| `404` | The referenced record doesn't exist |
| `429` | Rate limit exceeded (Lead Capture, anonymous requests only — a valid key exempts a request from this) |
| `500` | Unexpected server error — check rndCRM's own logs |

## 5. Adding a New Domain

This document is meant to grow — campaign sync, todo sync, task sync, etc.
— as they're built. The code side of that pattern (folder layout, shared
auth middleware, where to register a new router) is documented in
`backend/src/external-api/README.md`. When a new domain ships, add a
section here matching §2's structure: one subsection per endpoint, with a
field table and a real example request/response.
